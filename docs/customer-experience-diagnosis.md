# Customer experience diagnosis — 2026-10-16

Inspected main at `1affd07` before implementation.

* Discovery: `frontend/app/customer/plants.tsx` GETs `/customer/plants`; `backend/src/routes/mod.rs` registers GET `/api/customer/plants`. The handler lists all plants, with client-side distance ranking and no server radius/pagination. Google Places discovery is separate and user initiated. Review-fixture isolation must remain intact.
* HTTP 404: unauthenticated public `https://trackmyrmc.com/api/customer/plants` returns **401**, so the deployed public route exists. `/api/api/customer/plants` returns **404**. `src/api/client.ts` unconditionally appends `/api`, allowing exactly that failure with an API-prefixed environment URL. CI currently sets a bare origin. The original authenticated incident is not established without its request URL/deployed build configuration; do not claim a proven production root cause. The checked-in nginx proxy targets a Cloud Run preview despite the AWS deployment workflow; no infrastructure destination will be changed without verified runtime configuration.
* Maps: native `PlantMap.tsx` uses Google Maps but only sets initialRegion; web `PlantMap.web.tsx` is a static placeholder. No map-region discovery callback or manual location selector exists.
* Permissions: contextual foreground/background disclosures and Expo runtime APIs already exist. No first-install introduction or authenticated customer versioned consent gate exists. Discovery can re-prompt on mount. Push registration is Android-only and optional. Camera/POD permissions are contextual.
* Navigation: customer tabs authenticate correctly but lack Android root exit confirmation. Browser history should remain browser-managed.
* Tracking: driver task already supports active-trip foreground/background collection. Customer polls only when `active` is true, but Rust returns `order_status` and flat `loads`, whereas the UI requires `active`, `status`, `destination`, `active_loads`, nested `location`. The handler authorizes ownership but reads mixer-global last position, which may belong to another order after mixer reuse. Telemetry writes allow an omitted load_id. Repair contracts and bind telemetry to the assigned load before adding UI features.
* Privacy/security: preserve authentication, KYC/order enforcement, review-fixture separation, and existing driver disclosures. Send discovery coordinates in authenticated POST bodies, never navigation URLs; query only assigned-load telemetry for owned orders. Do not introduce customer background collection or fabricated ETA, price, stock, ratings, or delivery guarantees.

Verification needs an authenticated staging customer/driver, configured Google keys, PostgreSQL test database, and an Android device/emulator. Production release verification remains separate from code validation.
